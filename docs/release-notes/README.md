# 发布说明模板

每个版本一个文件：`docs/release-notes/<tag>.md`，只写这一版新增或改进了什么。

```markdown
## 新增与改进

- 中文条目一
- 中文条目二

## What's New & Improved

- English entry one
- English entry two
```

规则：

- 只有这两个小节，顺序固定，中文在前，英文在后；每条中文都有一条英文与之对应，条数必须相同。
- 只写用户看得见的功能与体验变化。内部测试数字、提交哈希、构建号、CI 与流程报告都不写进来。
- 修复也算「新增与改进」，写在同一个列表里，不另开小节。
- 下载与安装只由 `scripts/release-notes.sh` 在正文末尾补一句，并链接到该 tag 的 README；不要在正文里贴 Gatekeeper 或权限教程。
- 发布工作流在打包之前运行 `./scripts/release-notes.sh "$GITHUB_REF_NAME"`。文件缺失、小节缺失或顺序不对、多出小节、小节外有文字、某节没有条目、中英条数不一致时，发布直接失败（退出码 2，stdout 不输出半份正文），不会退回旧的安装说明。
- 尾句是脚本统一补的一句中性下载说明，只链接到该 tag 的 README，不提具体附件名与机型，因为早期版本发的是通用 zip、后来才是按架构的 DMG。

自动检查能做到的与做不到的：

- 只管结构：两个小节、顺序、每节至少一条、中英条数相同，外加一小串关键词（`个测试`、`独立复验`、`测试…通过`、`build 数字`、`sha256:`、`tests passed`、`test suite`、`all tests`）。
- 不管语义：中英是否真的一一对应、有没有被换个说法的内部报告混进来、功能是否属于这一版，都要人读。发布前请人工过一遍 `docs/release-notes/<tag>.md`。

## 生效范围

这些文件目前只在本地工作区：模板、校验脚本与工作流改动要**提交并推送**之后，才会约束以后的发布。远端已有的九个 Release 正文与资产本轮都不改，需要人按授权逐版更新。

格式自检：`./scripts/test-release-notes.sh`（`./scripts/test.sh` 也会跑一遍），目前 21 项检查：9 版正文 + 1 个正确样例的 3 项 + 8 个拒绝用例。
